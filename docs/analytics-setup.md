# Analytics setup — GA4, Microsoft Clarity, Search Console

Pedaver.com is a fully static export with no server (see `CLAUDE.md`), so
this is deliberately *not* a custom analytics backend. It's GA4 + Microsoft
Clarity, installed globally, plus a typed set of custom events. You view the
data in GA4's and Clarity's own free consoles — nothing here needs hosting
or maintaining beyond the code that sends the events.

Manual, account-level steps (the ones only a human can do) are marked
**→ You do this**.

---

## 1. Environment variables

All three are **public, build-time** values — Next.js inlines them into the
JS bundle at `npm run build` time. They are not secrets (GA measurement IDs
and Clarity project IDs are visible in any page's source on any site that
uses them), but a rebuild + redeploy is required any time one changes.

| Variable | Where it's used | Required? |
|---|---|---|
| `NEXT_PUBLIC_GA_MEASUREMENT_ID` | `GoogleAnalyticsScripts.tsx` — loads `gtag.js` | No — GA install is skipped (renders nothing) if unset |
| `NEXT_PUBLIC_CLARITY_PROJECT_ID` | `ClarityScript.tsx` — loads Clarity's bootstrap snippet | No — Clarity install is skipped if unset |
| `NEXT_PUBLIC_GSC_VERIFICATION` | `layout.tsx` metadata → `<meta name="google-site-verification">` | No — tag is omitted if unset (used only for the URL-prefix Search Console property, see §4) |

**→ You do this:** create `.env.local` at the project root (already
gitignored via the existing `.env*` pattern — never commit it) with:

```
NEXT_PUBLIC_GA_MEASUREMENT_ID=G-XXXXXXXXXX
NEXT_PUBLIC_CLARITY_PROJECT_ID=xxxxxxxxxx
NEXT_PUBLIC_GSC_VERIFICATION=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

Both people on the team (per `README.md` §7) need their own local copy of
these values. Share them out-of-band — a password manager entry or a
private note — never in a commit, an issue, or chat where it'd get pasted
into a file.

## 2. Create the accounts

**→ You do this**, in order:

1. **GA4 property** — [analytics.google.com](https://analytics.google.com) →
   Admin → Create Property → name it "Pedaver Website" → set up a **Web**
   data stream for `https://pedaver.com` (or the live domain). GA gives you
   the Measurement ID (`G-XXXXXXXXXX`) on the stream's detail page — that's
   `NEXT_PUBLIC_GA_MEASUREMENT_ID`.
2. **Microsoft Clarity project** — [clarity.microsoft.com](https://clarity.microsoft.com) →
   New project → name it, paste the site URL → Clarity gives you a Project
   ID in the setup instructions — that's `NEXT_PUBLIC_CLARITY_PROJECT_ID`.
3. In the Clarity project's **Settings → Masking**, turn on **"Mask all
   text and user input by default."** This is account-wide defense in depth
   on top of the explicit `data-clarity-mask="true"` attributes already in
   the code (§5) — belt and suspenders, since a future form added without
   the attribute would otherwise leak into a session recording.

## 3. Build and deploy

```bash
npm run build
```

then deploy as usual (`README.md` §6). Confirm live by viewing page source
on the deployed site and checking for `gtag/js?id=G-...` and
`clarity.ms/tag/...` script tags.

## 4. Google Search Console

Two properties, since PedaVer has DNS access — the Domain property is the
"real" one with full coverage; the URL-prefix property is a code-driven
backup that works the moment the site rebuilds, no DNS propagation wait.

### Domain property (DNS — recommended, do this one)

**→ You do this:**

1. [search.google.com/search-console](https://search.google.com/search-console) →
   Add property → **Domain** → enter `pedaver.com`.
2. Search Console gives you a TXT record value
   (`google-site-verification=...`). Add it as a **TXT record** at the
   domain's DNS host (whoever manages `pedaver.com`'s DNS — you or your
   son) with host `@` (or blank, per the registrar's convention).
3. Wait for DNS propagation (can take a few minutes to ~48 hours), then
   click **Verify** in Search Console.

### URL-prefix property (code — faster, no DNS wait)

1. In Search Console, Add property → **URL prefix** → enter the exact live
   URL (`https://pedaver.com`).
2. Choose the **HTML tag** verification method — it gives you a `content="..."`
   value. Set that value as `NEXT_PUBLIC_GSC_VERIFICATION` in `.env.local`
   (§1), then `npm run build` and deploy.
3. Once deployed, click **Verify** — Next's `metadata.verification.google`
   renders the tag automatically; no manual HTML editing needed.

### Sitemap and robots

Confirm both are reachable on the live domain (they're generated by
`src/app/sitemap.ts` / `src/app/robots.ts` if present, or served as static
files — check `out/sitemap.xml` and `out/robots.txt` after a build):

- `https://pedaver.com/sitemap.xml`
- `https://pedaver.com/robots.txt`

In Search Console → **Sitemaps**, submit `sitemap.xml`. Spot-check that a
few public routes (home, a paper, a crop) return 200 and have a correct
`<link rel="canonical">` pointing at their own URL (view source).

## 5. Privacy design

**What counts as PII here** (never sent as an event parameter): anything a
visitor typed into a form field, free-text search queries, anything
IP-derived beyond GA's own coarse geography. Crop/paper/machine/language
identifiers are fixed catalog values (e.g. `"wheat"`, `"ur"`), not personal
data.

How this is enforced, not just intended:

- **Enquiry/newsletter events structurally cannot leak form contents.**
  `trackEnquirySubmitIntent(source: "contact_form")` and
  `trackNewsletterSignupIntent()` never receive the name/email/message
  state from `ContactForm.tsx` / `NewsletterForm.tsx` in the first place —
  there's no parameter to accidentally pass.
- **Search text is never sent.** `trackInternalSearch(queryLength,
  resultCount)` only receives the *length* of what was typed and how many
  results matched — never the string itself.
- **Clarity field masking**: `data-clarity-mask="true"` is set explicitly
  on the name/email/message inputs in `ContactForm.tsx` and the name/email
  inputs in `NewsletterForm.tsx`, on top of the account-wide "mask by
  default" setting from §2.
- **IP anonymization**: `anonymize_ip: true` is set in the GA4 config call
  (`GoogleAnalyticsScripts.tsx`).
- **Enquiry events measure intent, not delivery.** Both forms build a
  `mailto:` link and hand off to the visitor's email client — there is no
  server to actually receive the message. `enquiry_submit_intent` /
  `newsletter_signup_intent` mean "visitor clicked submit and their email
  client opened," not "message received." Keep this in mind when reading
  these numbers in GA4 — they're an upper bound on real enquiries, not a
  count of them.

## 6. Full event catalog

Every custom event, fired via the single `track()` fan-out in
`src/lib/analytics/track.ts` (pushes to GA4's `dataLayer` and to Clarity's
custom-event queue in one call). Source functions live in
`src/lib/analytics/events.ts`.

| Event | Fires from | Parameters | Notes |
|---|---|---|---|
| `page_view` | `AnalyticsClientRoot`, on every pathname change (first load included) | `page_path`, `page_location`, `page_title`, + `traffic_source_category`/`ai_referrer` when the referrer matches a known AI tool | The *only* source of pageviews — GA's own automatic pageview is disabled (`send_page_view: false`) so there's nothing to double-count against |
| `content_view` | `ContentViewTracker` (mount) on paper/crop pages; `SectionViewTracker` (IntersectionObserver, 50% visible) on machine/resource articles | `content_type` (`paper`\|`crop`\|`machine`\|`resource`), `content_id` (slug), `content_title` | Machines/resources have no per-item URL, so this is the only signal for which one someone actually viewed |
| `pdf_download` | `TrackedPdfLink`, click | `content_id`, `content_title`, `file` (basename only, never a full path) | |
| `paper_external_link_click` | `TrackedExternalLink`, click | `content_id`, `publisher` | Journal-hosted papers, not our own PDF |
| `video_engage` | `VideoEmbed` (YouTube iframe), focus-detection proxy | `source: "youtube_embed"`, `video_id`, `context_type`, `context_id` | Cross-origin iframe — this is "focus moved into the player," not a real play event. See §7 caveat |
| `video_play` | `TrackedVideo` (self-hosted `<video>`), native `onPlay`, once | `source: "self_hosted"`, `context_type`, `context_id` | Real media event — same-origin |
| `video_progress` | `TrackedVideo`, native `onTimeUpdate`, once per milestone | `source: "self_hosted"`, `context_type`, `context_id`, `milestone` (25\|50\|75) | |
| `video_complete` | `TrackedVideo`, native `onEnded`, once | `source: "self_hosted"`, `context_type`, `context_id` | |
| `enquiry_submit_intent` | `ContactForm.tsx`, `handleSubmit`, before the `mailto:` navigation | `source: "contact_form"` | No form contents — see §5 |
| `newsletter_signup_intent` | `NewsletterForm.tsx`, `handleSubmit` | `source: "newsletter_form"` | No form contents — see §5 |
| `language_change` | `TranslateWidget.tsx`, `handleChange` | `target_lang` (ISO code), `current_path` | |
| `internal_search` | `Header.tsx`, search submit | `query_length`, `result_count`, `has_results` | No query text — see §5 |
| `related_content_click` | `TrackedRelatedLink`, click | `from_type`, `from_id`, `to_type`, `to_id` | Related crop/paper links on paper and crop pages |
| `external_channel_click` | `TrackedExternalChannelLink`, click | `destination_label`, `destination_host` | WhatsApp/Facebook/YouTube links on Services/Contact |
| `scroll_depth` | `useReadingDepth` hook, mounted globally via `AnalyticsClientRoot` | `depth` (25\|50\|75\|90), `page_path` | Fires once per threshold, resets on route change |

**No dedicated infographic event.** The only image on the site that could
be called an infographic (`/validation`'s process graphic) isn't
downloadable and has no click affordance — it's already covered by that
page's `page_view`/`scroll_depth`. If a real downloadable infographic is
added later, reuse the `pdf_download` shape.

## 7. Video tracking — two-tier, by design

- **Self-hosted `<video>`** (paper/machine video files): same-origin, so
  `video_play` / `video_progress` / `video_complete` are real native media
  events — accurate play/progress/completion data.
- **YouTube iframes**: cross-origin. The browser will not let real
  play/pause events bubble out of a YouTube iframe into the parent page
  without loading YouTube's separate IFrame Player API (a real script
  dependency this project deliberately doesn't take on). `video_engage` is
  a focus-detection proxy instead — it tells you a visitor's focus moved
  into that specific player, not whether they watched any of it. Read GA4
  reports on `video_engage` with that caveat in mind; it is not comparable
  to `video_play`/`video_progress` numbers.

## 8. AI referral classification

`src/lib/analytics/aiReferrers.ts` checks `document.referrer`'s hostname
against a small list of known AI-tool domains (ChatGPT, Claude, Perplexity,
Gemini, Copilot, You.com, Poe) on the first `page_view` of a session. A
match adds `traffic_source_category: "ai_referral"` and `ai_referrer:
"<tool>"` to that event — filterable in GA4 as a custom dimension/segment
without hand-building a referrer regex.

**Honest limit**: this only catches sessions where the AI tool actually
passes a Referer header when a visitor clicks a link. Several chat
interfaces strip it, and a copy-pasted link carries no referrer at all.
This under-counts AI-driven traffic; it is a best-effort signal, not a
complete picture.

## 9. Knowledge Engagement Score (KES) — a formula, not a dashboard widget

There's no server to compute a live number, so this is a manual pull from
GA4's own reports, combining metrics already being collected into one read
on "are visitors actually learning here" — which fits Pedaver's mission
better than raw traffic:

| Component | Where to find it in GA4 |
|---|---|
| Reading completion rate | Events → `content_view` vs `scroll_depth` where `depth=90`, same `page_path`, as a ratio |
| Average engagement time | Engagement → Pages and screens (GA4's own native per-page metric — no custom event needed) |
| `pdf_download` rate per paper | Events → `pdf_download`, segmented by `content_id` |
| `video_engage` / `video_play` rate per video | Events → filtered by event name, segmented by `context_id` |
| `enquiry_submit_intent` rate per session | Events → `enquiry_submit_intent` ÷ Sessions — the strongest signal of the four |

Pull these periodically (monthly is reasonable) rather than trying to
automate them — automating this is a natural future extension if it's ever
worth the engineering time, not something built now.

**Deliberately left out, with reasoning** (from an earlier proposal to
extend this further):

- **Timer-based engagement (30s/60s/3min/5min) and scroll velocity** — GA4
  already computes engaged sessions and average engagement time natively.
  Custom timers would duplicate a metric already available for free.
- **"Print," "share," infographic "enlarge," breadcrumb usage tracking** —
  none of these UI features exist on the site today. Instrumenting
  features that aren't there isn't testable.
- **A formal multi-provider plugin/adapter system** — `track()` in
  `src/lib/analytics/track.ts` is one function that fans out to GA and
  Clarity. Adding a third provider later means adding one call inside that
  function, not building a plugin architecture speculatively today.
- **A custom `/admin/analytics` dashboard** — would need a server to keep
  GA4 Data API credentials secret; this site has none. GA4's and Clarity's
  own consoles already cover every metric requested, for free, with
  nothing new to host.

## 10. Where to find each metric in GA4 / Clarity

| You want... | Where |
|---|---|
| Visitors, sessions | GA4 → Reports → Realtime / Life cycle → Acquisition |
| Countries | GA4 → Reports → User → Demographics → Overview (map) |
| Devices | GA4 → Reports → User → Tech → Overview |
| Acquisition channels (search/direct/referral/social/AI) | GA4 → Reports → Acquisition → Traffic acquisition |
| Top pages | GA4 → Reports → Engagement → Pages and screens |
| Paper/PDF/video engagement | GA4 → Reports → Engagement → Events, filter by event name (`content_view`, `pdf_download`, `video_engage`, etc.) |
| Enquiries | GA4 → Events → `enquiry_submit_intent` / `newsletter_signup_intent` |
| Language usage | GA4 → Events → `language_change`, secondary dimension "target_lang" (custom parameter — see note below) |
| Reading depth | GA4 → Events → `scroll_depth`, secondary dimension "depth" |
| AI referrals | GA4 → Events → `page_view`, filter where `traffic_source_category = ai_referral` |
| Session replays | Clarity → Recordings |
| Rage clicks / dead clicks | Clarity → Dashboard (computed automatically) |

**Note on custom parameters**: GA4 doesn't show custom event parameters
(like `target_lang`, `content_id`, `depth`) in reports by default — they
need to be registered once as **custom dimensions** (Admin → Custom
definitions → Create custom dimension, scope "Event") before they're
available as report dimensions. Do this for the parameters you want to
segment by; it only needs doing once per parameter, and it can't be
scripted from a static site.

## 11. Pre-deployment testing checklist

1. **GA4 DebugView**: install the [GA Debugger extension](https://chrome.google.com/webstore/detail/google-analytics-debugger)
   or add `?_dbg=1`-style debug mode, open GA4 → Admin → DebugView, browse
   the site, and confirm events appear in real time with the expected
   parameters.
2. **Dedup check**: navigate between a few pages and confirm exactly one
   `page_view` fires per navigation — no duplicate on first load.
3. **Clarity live session**: browse the site with a test Clarity project
   ID, then check Clarity → Recordings for a session, and confirm the
   name/email/message fields show as masked (blocked out), not the typed
   text.
4. **Search Console**: confirm both verification paths succeed (or at
   least the URL-prefix one, if DNS is still propagating), and that
   `sitemap.xml`/`robots.txt` are reachable and the sitemap is accepted
   with no errors.
5. **Click through every instrumented surface once** and confirm the
   documented event fires with the documented shape, and nothing else:
   PDF download, a YouTube embed, a self-hosted video, the contact form,
   the newsletter form, the language switcher, an internal search, a
   related-content link, an external channel link (WhatsApp/Facebook/
   YouTube).
6. **Scroll a long page** (e.g. a Knowledge Paper) and confirm
   `scroll_depth` fires at 25/50/75/90 and not before/after.
7. **Inspect outgoing payloads** (Network tab, filter `collect` for GA4 or
   the Clarity requests) for all of the above and confirm no PII-shaped
   values appear — no names, emails, message text, or search query text.
8. **Verify the `google-site-verification` meta tag** renders in page
   source when `NEXT_PUBLIC_GSC_VERIFICATION` is set, and confirm it's
   absent (not an empty tag) when unset.
