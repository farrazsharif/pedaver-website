A

Ask PQNK backend hosting

The service is a hand-rolled node:http server with server-rendered Inbox views and a node:sqlite file on disk — a real, stateful, always-listening process, not a set of stateless functions. That shape decides most of this section before cost even enters the picture.

Why serverless is ruled out, not merely disfavored: node:sqlite needs a durable, always-attached local disk. Lambda, Vercel Functions, and Cloudflare Workers give either no filesystem or a wiped one between invocations. Running there would mean rewriting the persistence layer first (see §B) — that's a database decision forcing an architecture change, not a hosting preference.

Environment secrets — every one of these platforms provides an encrypted env-var store in its dashboard, which is exactly the mechanism the code already expects (ANTHROPIC_API_KEY, ASK_PQNK_SESSION_SECRET, ASK_PQNK_PEDAVER_PASSWORD are all read from process.env today). Traffic fit — at low/moderate initial volume, the smallest tier of either a VPS or a PaaS persistent-volume service is genuine overkill in raw compute and comfortably enough in practice. A verdict — approved: Render. A small Render Web Service with a persistent disk — same code, zero rewrite, HTTPS and api.pedaver.com in the dashboard rather than a manual cert pipeline, and low enough lock-in that moving to a VPS later is a weekend project, not a migration. Exact setup in §J.
B

Production database

The local build already runs SQLite in WAL mode (PRAGMA journal_mode = WAL — already set in db.ts), which is what makes option 1 viable at all: WAL allows concurrent readers alongside a single writer, and Ask PQNK's actual write pattern — Pedaver publishing occasionally — never approaches that limit.

1 · Retain SQLite, persistent volume recommended

Zero code change. One file, trivial mental model, fast for this read-heavy / rarely-written workload. Requires a host from §A that mounts a genuinely persistent disk — this is the one hard constraint the local-file design imposes on hosting choice.

2 · Move to PostgreSQL

Real multi-writer concurrency and mature tooling, but a data-layer rewrite for a concurrency problem V1 doesn't have. The existing prepared statements map cleanly to pg/postgres.js later — this is deferred work, not avoided work.

3 · Managed database service

The natural landing spot if/when 1 stops being enough — managed Postgres add-ons exist on every platform in §A with a few minutes' setup. Not a V1 decision; a documented next step.

The constraint that governs all three

Local-file SQLite is fine on durable attached storage and actively unsafe on ephemeral/serverless storage. This is exactly why §A ruled out FaaS hosting — the two decisions are coupled, not independent.

Persistence, backup, concurrency, migration
  • Persistence — one file on a mounted volume that survives redeploys and restarts (every PaaS option in §A supports this).
  • Backup/restore — covered fully in §E; SQLite's single-file shape makes this simpler than a running Postgres server, not harder.
  • Concurrency — WAL-mode SQLite handles Ask PQNK's actual shape (many readers, rare single writer) without contention, provided exactly one app instance is running. Approved as a locked constraint, not just a preference: Render's persistent disks attach to a single instance by design (no multi-instance disk sharing), which happens to enforce the same constraint SQLite already needs — the platform default and the database requirement point the same direction.
  • Migration path — well-defined and deferred: move to managed Postgres when either write-concurrency or horizontal app scaling becomes a real, measured need — not a speculative one.
  • Operational burden — near zero for SQLite (no separate DB process to patch, secure, or monitor); Postgres, even managed, is a second service with its own connection limits, dashboard, and monthly line item.
  • Cost — SQLite: $0 beyond the disk you're already paying for. Managed Postgres: commonly $7–25+/mo at the smallest usable tier.
B verdict: retain node:sqlite on a persistent attached volume for V1. It is not a compromise — it is the simplest architecture that correctly matches this specific read-heavy, low-write workload, provided (and only provided) the host in §A actually gives it durable storage.

Production authentication

The local build's auth.ts is intentionally minimal: one shared password from an env var, an HMAC-signed session cookie, no throttling, no CSRF token. Production needs to close those gaps for a handful of named Pedaver reviewers — not replace the approach with an identity platform it doesn't need.

Every item is a modest, well-understood addition to code that already exists; none of it calls for OAuth, SSO, or a managed identity provider for two or three named users.
E

Backup & recovery

Farmer Advisory knowledge, the referral queue, question clusters, and private contact/context data all live in the same SQLite file, in their already-separated tables (§F) — so a file-level backup captures all four categories in one consistent, atomic snapshot.

Render's built-in disk backups recommended for pilot

Render's persistent disks include automatic daily backups, restorable from the dashboard, at no extra cost beyond the disk itself — zero new services, zero new credentials, fits the approved conservative pilot budget exactly. Confirm the current retention window in Render's own docs when setting the disk up.

Litestream → R2/B2 future upgrade

Continuous WAL streaming to S3-compatible storage, near-real-time point-in-time restore. The stronger option once Farmer Advisory content is valuable enough to justify tighter recovery points than a daily snapshot — not required to launch the pilot, deferred to keep this round's budget conservative.

Restore time — Render disk restore from the dashboard: minutes, with up to 24h of possible loss (bounded, in practice, by how rarely Pedaver actually publishes — see the tested procedure in §J, which uses the same mechanism a Render restore relies on internally: a consistent file-level snapshot, safely swapped in while the app is stopped).

Data-retention note, not resolved here: because contact/context data shares the same file as public knowledge, any future retention or deletion policy for personal contact info (§13 of the referral workflow) should also account for how long old backups are kept. That's a policy call for Pedaver, not an infrastructure one — flagged so it isn't missed later.
E verdict — approved for pilot: Render's built-in disk backups. Zero extra cost, zero extra services, matches the $10–25/mo budget precisely. Litestream stays the documented upgrade path once real corpus value justifies it. The restore procedure itself has been rehearsed end-to-end — see §J.
F

Production data separation

Already true today, not a production-only concern — confirmed directly in the schema and the local hardening pass, carried forward unchanged.

  • Public Farmer Advisory knowledge — farmer_advisory table only; never contains contact fields; the only two public read endpoints (/api/advisory, /api/advisory/:id) select from it exclusively.
  • Private referral/contact data — structurally separate in referral_queue, never exposed by any public endpoint, readable only through the authenticated Inbox.
  • Authentication/secrets — environment variables only, never in the database, never in the git repo, never returned by any response body.
  • Logs — one production rule to carry forward that doesn't exist as code yet: request/error logging must never dump full request bodies for /api/refer, since that would leak contact fields into log storage even though the database schema keeps them properly separated. Log the outcome and the reference number, not the submitted contact object.
F verdict: the separation is a property of the schema already, not something production introduces — the one new item is a logging-hygiene rule for whoever wires up the production log pipeline.
G

Migration from local development

The local ask-pqnk.sqlite file is a development and testing artifact — as of this session's teardown-tested acceptance suite, it holds zero rows in all three tables. It should never be the seed for production.

  1. Never copy the local .sqlite file to production. It is already gitignored (data/*.sqlite, confirmed untracked) and should stay outside any deploy artifact entirely.
  2. Production starts from the schema, not a file. db.ts's CREATE TABLE IF NOT EXISTS statements run automatically on first boot against a fresh, empty volume — production is correctly empty on day one with no manual seeding step.
  3. Any genuine day-one content goes through the real pathway. If Pedaver wants to seed a few known common answers before the first real farmer question arrives, those are authored through the same /inbox/:id/publish action (or an explicit, clearly-labeled one-time seed script that constructs records with real provenance) — never a raw copy of anything from local testing.
  4. Pre-deploy checklist item: confirm the production database path/connection string points at a new, empty target before the first deploy, as a deliberate gate rather than an assumption.
G verdict: production inherits the schema, never the file — the clean corpus requirement is satisfied by how the app already boots, not by anything extra that needs building.

J.4 — Pre-deploy code readiness checklist Not yet done

Three small, low-risk changes to ask-pqnk-service, identified while preparing this exact plan. None have been made — they need your go-ahead like any other code change, separate from the infrastructure approval above.

  • Port binding. server.ts currently reads ASK_PQNK_PORT; Render injects and expects PORT. One-line fix: Number(process.env.PORT ?? process.env.ASK_PQNK_PORT ?? 4001) — keeps local dev unchanged, makes Render's routing work.
  • Data directory. db.ts currently resolves the SQLite path relative to its own compiled location, not to any env var. Add ASK_PQNK_DATA_DIR, defaulting to today's relative path when unset (zero effect on local dev), and point it at /data in Render — this is what makes the persistent disk actually the disk the app writes to, rather than an unused, unrelated mount.
  • Health check route (optional) — a trivial GET /healthz returning 200 with no DB access, or skip this and point Render's health check at the already-public /api/advisory instead.

J.6 — Backup & restore procedure ✓ Tested, this session, against a real copy of the schema

Render's built-in disk backups (§E) handle the routine case automatically. The procedure below is what a manual restore looks like — for a pre-migration checkpoint, or if the automatic backup needs to be pulled and verified by hand. It was rehearsed just now against the actual local development database (which was already confirmed empty of real data), not against a hypothetical.

1
Opened the DB, inserted a marker record with full provenance fields, took a consistent snapshot with SQLite's own VACUUM INTO, closed the connection.Snapshot: 45,056 bytes — succeeded.
!
First attempt found a real bug in the naive procedure. Swapping only the main .sqlite file while stale -wal/-shm sidecar files remained (and, separately, while a background process still held the database open) produced PRAGMA integrity_check failures and silently missing data.integrity_check: "wrong # of entries in index idx_queue_cluster"
2
Corrected procedure: confirmed the app process was fully stopped, then removed all three files together — .sqlite, .sqlite-wal, .sqlite-shm — before restoring, since a WAL file is tied to a specific base file's state and a mismatched pairing is exactly what caused the corruption above.
3
Copied the snapshot in as the new main file. Reopened.PRAGMA integrity_check → "ok"
4
Verified the marker record restored with every provenance field intact.{ id: "backup-drill-marker", approved_by: "Pedaver", publication_status: "Published", origin_reference_number: "PQNK-Q-DRILLTEST" }
5
Removed the marker and the drill snapshot; confirmed the database returned to its exact prior state.{ advisory: 0, queue: 0, cluster: 0 } — matches baseline

The procedure, as it must be followed in production:

  1. Stop the app instance (Render dashboard → Suspend, or scale to zero) before touching any database file directly. An open connection holding a live WAL is what turned a routine file swap into corruption during this drill.
  2. Take or retrieve a snapshot. Either Render's own daily disk backup, or a fresh manual one via VACUUM INTO if the app can still be reached (e.g. a one-off admin script) before stopping it.
  3. Remove all three live files — the main .sqlite file and its -wal/-shm siblings, if present — never just the main file alone.
  4. Copy the snapshot in as the new main file.
  5. Restart the app — a clean boot with no stale sidecar files will recreate fresh, empty WAL/SHM files on first write, exactly as local dev already does.
  6. Verify — run PRAGMA integrity_check and spot-check a known record before considering the restore complete.
What this drill actually proved: the difference between "described" and "tested" here was concrete — the first documented instinct (swap the file, done) is exactly wrong for a WAL-mode database, and running it for real is what surfaced that before it could happen against real Farmer Advisory content.
J.7 — Rollback plan
  • Application rollback — Render retains deploy history; rolling back is redeploying the previous successful build from the dashboard, one action.
  • Database rollback — restore from the most recent Render disk backup (or a manual pre-change snapshot, J.6) using the tested procedure above.
  • Before any schema-affecting deploy (adding a column, as happened during this engagement's own local hardening pass): take a manual VACUUM INTO checkpoint first, as cheap insurance, before applying the change.
  • Schema changes are never automatic in production. db.ts's CREATE TABLE IF NOT EXISTS is additive-only — a new column needs one explicit, deliberate ALTER TABLE run against the production database, exactly mirroring how it was done locally this session (never a blind drop/recreate against a database holding real records).
