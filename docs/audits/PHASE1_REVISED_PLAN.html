P0Fix sitemap lastmod for externally-cited papers
What changes
For papers carrying externalUrl (real third-party citations, e.g. the 2011 Springer SRI paper), stop using publishedDate as the sitemap lastmod — use the same build-time signal as other content types instead

Benefit
Accurate freshness signal for search engines deciding re-crawl priority
Risk

P1

Knowledge Paper machine understanding

How search engines and AI systems read what a Knowledge Paper actually is, backed by content that genuinely appears on the page.

UrgentP1Rewrite the "Requires PQNK Review" messaging — it currently contradicts decision 7 live, today

Found while scoping this plan, not previously flagged: the paper page's visible banner for this status currently reads —

"PQNK Review Status — this paper contains one or more statements currently under Pedaver/PQNK review. It remains available as part of the Knowledge Library, but flagged statements should not be treated as current authoritative PQNK doctrine until review is complete."

This is live, visible text on 54 real pages, telling both human readers and any crawler/AI system reading the page that its content should not be treated as authoritative — the exact framing decision 7 corrects. Two shorter badge labels elsewhere ("Under PQNK Review") are less actively wrong but should be updated for consistency.

What changes
Rename the status value everywhere it's stored; rewrite the banner and both badge labels to reflect "knowledge authenticated, wording/consistency review pending" — e.g. banner: "This paper's PQNK knowledge is authenticated. Wording, terminology, and presentation consistency across the site are still being finalized." Badges: "Editorial Review Pending."
Why
Decision 7 — the underlying knowledge must not be characterized as provisional; this page currently does exactly that, to visitors and machines alike, right now
Benefit
Removes an active, live signal that could cause a crawler or AI system to decline to cite 54 genuinely authoritative papers (29% of the corpus) — directly serves the outreach objective, not just internal consistency
Risk
Low. The comparison logic (authorityStatus === REQUIRES_REVIEW) is done via the exported constant, not a hardcoded string, in every file that uses it on the live site — confirmed in page.tsx, PapersBrowser.tsx, RelatedKnowledgeModule.tsx — so changing the constant's underlying string value is safe for those. Known, deliberately deferred consequence: the paused Ask PQNK backend (ask-pqnk-service/src/retrieval.ts, scripts/export-content.ts) and its docs hardcode the literal old string directly, not the constant — they will silently stop matching this status once renamed. Not fixed here (Ask PQNK is paused); flagged to reconcile only if/when it resumes.
Visible to visitors?
Yes — the banner and badge text change on 54 pages; the underlying content of those pages does not
Files: src/lib/content/knowledge/taxonomy.json, src/lib/content/knowledge/taxonomy.ts (REQUIRES_REVIEW value), src/lib/content/knowledge/metadata.json (54 entries), src/app/papers/[slug]/page.tsx (banner text), src/app/papers/PapersBrowser.tsx (badge text), src/components/science/RelatedKnowledgeModule.tsx (badge text)

P1Add a visible Topics row (crops/domains/problems), then mirror it into JSON-LD keywords

New finding: crops, science domains, and field problems are already fully tagged in metadata.json for every paper, but are currently not displayed anywhere on the paper page — confirmed by inspecting the template. Adding them to structured data without first making them visible would repeat exactly the "hidden content" problem decision 4 warns against for discovery questions.

What changes
Add a small tag-pill row to the paper page (e.g. "Topics: Wheat · Water · Poor Water Infiltration"), reusing the visual pattern already established by the existing Authority badges; mirror that same, now-visible set into the page's JSON-LD keywords
Why
Genuinely useful to a human reader scanning a paper's subject at a glance, and only then a legitimate, standards-consistent basis for structured-data keywords — satisfies decision 4's "must accurately describe visible content" standard in both directions
Benefit
Real reader utility plus a defensible topical signal for search/AI systems — directly serves "machine-readable taxonomy and topical relationships" from decision 8's priority list
Risk
Low — purely additive, and the tags are the paper's own real, already-approved classification, not invented
Visible to visitors?
Yes — new tag row on 186 pages
Files: src/app/papers/[slug]/page.tsx
P1Infrastructure for editorially-selected visible Discovery Questions

P2Fix crop→paper matching to use structured data instead of title text-search

Benefit

Risk

P3Decide and apply an explicit AI-crawler robots.txt policy
What changes
Currently every crawler (search and AI-training alike) is allowed identically by one wildcard rule. A deliberate policy — e.g. allow OAI-SearchBot/Claude-SearchBot/PerplexityBot/Googlebot (citation-eligible) while deciding separately on GPTBot/ClaudeBot/Google-Extended/CCBot (training-only) — is a real, documented option per each vendor's own robots.txt guidance
Why
The current config is a default, not a decision
Benefit
Turns an accidental default into a deliberate choice, without narrowing citation-eligibility either way
Risk
None technically; the only open question is the policy itself, which is Pedaver's call, not a technical one — this item cannot proceed until that's answered
Visible to visitors?
No
Files: src/app/robots.ts
