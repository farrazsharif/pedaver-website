Correction: questionsAnswered Provenance and Use

The prior audit's framing was wrong on a material point and is corrected here before Phase 1 proceeds. The 1,041 questionsAnswered entries are not farmer questions — they are discovery-metadata questions a paper may be capable of answering. This document verifies that distinction from the repository, quantifies and quality-checks the field, and separately establishes which papers do have genuine, evidenced farmer-question origin.

1

Corrected finding

The prior audit's error: it described the 1,041 (previously misreported as 1,027 — corrected count below) questionsAnswered entries as "1,027 real, farmer-phrased questions" and implied their existence was evidence of Q&A-origin content across the corpus. That was an overreach not supported by what the repository actually documents.
Verified fact

src/lib/content/knowledge/taxonomy.ts's own doc comment (lines 4–10) describes this data in its own words: "This data is generated from the approved Controlled Vocabulary & Taxonomy 1.1 package... It is a DISCOVERY/INDEX layer on top of the original Knowledge Paper content in papers.ts — joined by slug, never merged into it." This is a repository-authored description of what the field is, and it says discovery/index layer, not farmer question log.

Inference, not fact

The source "Controlled Vocabulary & Taxonomy 1.1 package" and a referenced normalized_classification.json are named in that comment but do not exist anywhere in this repository — only their generated output (taxonomy.json, metadata.json) is committed. This means the actual generation process is not independently auditable from the repo; the doc comment's description is the best available first-party account, and it is corroborated (not contradicted) by every other piece of evidence in this report.

Corrected statement for the record: the 186 Knowledge Papers are authentic PQNK knowledge. The large majority were not written in direct response to a specific farmer's question. A small, identifiable set (§6) genuinely was. The questionsAnswered field is retrieval/discovery metadata — plausible, on-topic, well-formed questions a paper is capable of answering — generated as part of a taxonomy build process, not a transcript of real incoming questions.

Overstatement risk: without reading all 186 full papers, this can't be fully verified at scale — flagged as inference-level in §5's sample, where a handful of questions read as broader or more analytically framed than what a typical single paper would fully resolve on its own (e.g. sweeping comparative questions like "What's the difference between PQNK, Conservation Agriculture, Organic Certification, and Regenerative Agriculture?").

The prior recommendation ("render all 1,041 as visible 'Questions this paper answers'") is suspended. Replaced with a role-separated approach.

RoleRecommendationWhy
1. Internal semantic/retrieval metadataKeep as-isAlready working well for this purpose (client-side search, relatedness) — no change needed
2. Structured machine-discovery signal (JSON-LD)Yes, expose — as metadata, not as attributed speechSurfacing these as keywords or within an expanded description in each paper's ScholarlyArticle JSON-LD gives search/AI systems the retrieval benefit without any claim about who asked them — this is the safest, highest-leverage part of the original recommendation and should proceed
3. Visible human-facing "Questions this paper answers" contentSelective, not blanketPer §5, roughly three-quarters read naturally enough for direct display; the rest read as analytical/comparative framing better left as metadata. A blanket render of all 1,041 risks displaying a meaningful minority of oddly-scoped or overstated questions. 4. Search landing/query languageYesLegitimate use for informing which real search phrasings to target editorially (§9), and for the query-benchmark work already underway
5. Farmer Advisory ⇄ Knowledge Paper cross-linkingOnly for Tier 1/2, not genericallyReserve genuine "Farmer Question → Answer" framing for papers with real provenance (§6); use ordinary taxonomy-based relatedness (already built, related.ts) for the rest
What search engines and AI systems actually gain from role 2, concretely: not "more question sentences = better ranking" (no evidence supports that mechanism, and the prior audit should not have implied it). The genuine, documented mechanism is retrieval matching: a search or AI system matches a user's query against a page's actual text and metadata. Pages currently carry none of this question-form vocabulary anywhere machine-readable — adding it as keywords/description content gives the retrieval system more of the farmer's likely phrasing to match against, which is a real, well-understood mechanism (vocabulary overlap between query and indexed content), not a ranking trick. This is a modest, honest improvement — not a guarantee of appearing in results, and not a substitute for the genuine authority/backlink/usage signals discussed in the original audit's broader roadmap.
8

Status terminology: correcting "Requires PQNK Review"

Verified fact

taxonomy.json's authorityStatuses array carries no description text — it is 4 bare strings: Current / Approved PQNK Knowledge, Historical PQNK Formulation, External Knowledge / Evidence, Requires PQNK Review. There is a structurally separate field, evidenceType, already carrying values like "Scientific Mechanism," "Field Observation," "Farmer Testimony" — i.e. the taxonomy already has a dedicated axis for the evidentiary character of a paper's content, distinct from authorityStatus. This is consistent with (though doesn't independently prove) your clarification that authorityStatus was never meant to encode scientific/evidentiary provisionality.

A genuine tension worth flagging directly: docs/ask-pqnk/SOURCE_AUTHORITY_POLICY.md §2 (written earlier in this engagement, for the now-paused Ask PQNK system) describes this exact status as Tier 5, "Any source type, not yet vetted" — ranked below even "External Knowledge / Evidence." That phrasing does read as describing evidentiary/authority provisionality, which is exactly the misreading this correction is fixing. This was this engagement's own prior interpretation, not something invented by the earlier audit in isolation — it should be reconciled if Ask PQNK is ever resumed, so a future retrieval decision doesn't accidentally treat "editorial review pending" as "unreliable knowledge." Not touched now, per the no-implementation instruction — flagged for the record.

54 of 186 papers (29%) currently carry this status. Per your correction: none of these should be suppressed, downgraded in authority, excluded from search/AI discoverability, or excluded from the questionsAnswered work in §7 solely on this basis.

Recommended replacement

Your proposed direction — PQNK Authenticated — Editorial Consistency Review Pending — is a strong fit against the existing architecture: it's the same length/register as the other 3 canonical values, doesn't collide with evidenceType's job, and removes the "not yet vetted" ambiguity directly. Two adjacent options if a shorter label is preferred for UI space:

  • PQNK Knowledge — Editorial Review Pending (shorter, keeps "PQNK Knowledge" as the anchor phrase)
  • Approved Knowledge — Wording Review Pending (leans on "Approved" to explicitly borrow authority language from the Current / Approved status, making the contrast — approved content, pending polish — unmistakable)

Whichever wording is chosen, it should propagate to: taxonomy.json's authorityStatuses array, every metadata.json entry currently set to the old value (54 papers), taxonomy.ts's REQUIRES_REVIEW constant (rename or keep the constant name and only change its string value — constant renaming is a larger, riskier change than a value change), and — separately, later, only if Ask PQNK resumes — a reconciling update to SOURCE_AUTHORITY_POLICY.md §2's Tier 5 description. None of this is implemented in this pass.
